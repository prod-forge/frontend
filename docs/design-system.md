## What a Design System Is Here

A design system in this repository is a chain of layers. Each layer knows only about the one below it:

```text
design-tokens  ->  ui-web components  ->  ui-web widgets  ->  apps
(JSON values)      (stateless pieces)     (forms, composed)   (web-client, mobile-client)
```

- **Tokens** are the values: colors, spacing, radii, typography, shadows, transitions. They live in `packages/design-tokens`.
- **Components** are small stateless UI pieces such as `button`, `input`, `todo-item`. They live in `packages/ui-web/src/components`.
- **Widgets** are larger pieces assembled from components, such as `login-form` or `add-todo-form`. They live in `packages/ui-web/src/widgets`.
- **Apps** wire widgets to state and routing. `apps/web-client` uses `ui-web` and the CSS tokens. `apps/mobile-client` is a React Native app: it cannot use web components, so it shares only the tokens.

The rule that holds the chain together: a layer never imports from a layer above it. Tokens know nothing about components, and `ui-web` knows nothing about the apps.

This chapter is about the mechanics. The "why a design system at all" part, and the Tailwind decision, are in [Styles Management](styles-management.md).

## Token Pipeline

Tokens are authored as JSON in the [W3C design token format](https://tr.designtokens.org/format/) (`$value`, `$type`):

```json
{
  "space": {
    "1": { "$value": "4px", "$type": "dimension" },
    "2": { "$value": "8px", "$type": "dimension" }
  }
}
```

The files are in `packages/design-tokens/src/tokens/`:

| Path                             | Content                                                             |
| -------------------------------- | ------------------------------------------------------------------- |
| `base/*.json`                    | Theme-independent: spacing, radius, typography, layout, transitions |
| `color/light.json`, `dark.json`  | Color palette per theme                                             |
| `shadow/light.json`, `dark.json` | Shadows per theme                                                   |

[Style Dictionary](https://styledictionary.com) reads them with `packages/design-tokens/style-dictionary.config.mjs` and produces two outputs:

```text
src/tokens/**/*.json
        |
        v   npm run design-token:build
  Style Dictionary
        |
        +--> tokens.css        CSS custom properties, for web
        +--> js/index.mjs      nested JS objects, for mobile
             js/index.d.ts     TypeScript declarations for the above
```

The two outputs are deliberately different, because the platforms need different things.

For web, `tokens.css` has a `:root` block with base and light values, a `[data-theme='dark']` block, and a `prefers-color-scheme: dark` media query for users who have not chosen a theme. The theme segment is stripped from the name, so `color.light.bg` and `color.dark.bg` both become `--color-bg`.

For mobile, `js/index.mjs` exports plain objects (`color.light.bg`, `space[4]`). Dimensions are converted to unitless numbers (`"4px"` becomes `4`), because React Native `StyleSheet` does not accept units. The `.d.ts` file is generated by the same script, so mobile code gets typed tokens without a hand-written mirror.

### Why Generated Files Are Committed

`tokens.css`, `js/index.mjs` and `js/index.d.ts` are in git, even though they are generated. The reasons:

- a fresh clone works after `npm install`, with no build step before Storybook or Metro can start;
- a token change shows up in the pull request as a readable CSS diff, so a reviewer sees exactly which pixels move.

The price is that a source change and its generated output must be committed together. There is no check in this repository that fails when they drift apart (the pre-commit hook only runs lint-staged). That is a known gap: if you edit a JSON file and forget the build, nothing will stop you.

### How to Add a Token

1. Add the value to the right JSON file. A new color needs both `color/light.json` and `color/dark.json`, with the same key:

   ```json
   "info": { "$value": "#0369a1", "$type": "color" }
   ```

2. Run the build:

   ```shell
   npm run design-token:build
   ```

3. Check the diff of `tokens.css` and `js/index.mjs`. The variable should appear in `:root` and in the dark block.
4. For web, expose it to Tailwind in `packages/styles-web/src/theme.css` if components need a utility class (see the next section).
5. For mobile, nothing to do for colors: `color.light` and `color.dark` are consumed as whole objects by `apps/mobile-client/src/theme/tokens.ts`.
6. Commit the JSON and the generated files together.

## Theming

Both themes are defined by tokens. The three layers of theming on web are:

**1. CSS variables per theme.** `tokens.css` switches values when `<html data-theme="dark">` is set. Without the attribute, the media query follows the operating system.

**2. Tailwind mapping.** `packages/styles-web/src/theme.css` maps raw token variables to semantic Tailwind names using `@theme inline`:

```css
@theme inline {
  --color-page: var(--color-bg);
  --color-fg: var(--color-text-primary);
  --color-brand: var(--color-accent);
}
```

Components use `bg-page`, `text-fg`, `bg-brand`. The `inline` keyword matters: Tailwind emits `var(--color-bg)` instead of a resolved value, so the class follows the theme when the attribute changes at runtime. Components never mention a hex value or a theme.

**3. Applying the theme before first paint.** If the theme were set by React after mount, a dark-mode user would see a light flash. `apps/web-client/src/theme-init.ts` is loaded from `index.html` before `main.tsx`:

```ts
const stored = localStorage.getItem('theme');
const prefersDark = window.matchMedia('(prefers-color-scheme: dark)').matches;

document.documentElement.dataset.theme =
  stored === 'dark' || stored === 'light' ? stored : prefersDark ? 'dark' : 'light';
```

It is a module file and not an inline script on purpose: the Content Security Policy allows only `'self'` scripts. After mount, the `useTheme` hook in `packages/ui-web/src/hooks/theme/use-theme.ts` takes over: it reads the same `localStorage` key, toggles the attribute, and persists the choice.

Storybook uses the same mechanism. `packages/ui-web/.storybook/preview.ts` has a `theme` toolbar global and a decorator that sets `data-theme` on the document, so every story can be viewed in both themes.

### Mobile

React Native has no CSS variables. `apps/mobile-client/src/theme/tokens.ts` builds `lightTheme` and `darkTheme` objects from `design-tokens/js`, and `src/hooks/use-theme-tokens.ts` picks one:

```ts
export const useThemeTokens = (): ThemeTokens => (useColorScheme() === 'dark' ? darkTheme : lightTheme);
```

Mobile follows the system setting and has no manual toggle. The source of values is the same JSON, so a brand color changed in one place changes on both platforms.

## Component Anatomy

Every component and every widget in `packages/ui-web/src` is a folder with five files. The newest example is `todo-item`:

```text
packages/ui-web/src/components/todo-item/
  todo-item.tsx            the component
  todo-item.test.tsx       unit test (Vitest, jsdom)
  todo-item.stories.tsx    states as Storybook stories
  todo-item.a11y-spec.ts   axe-core check per story (Playwright)
  todo-item.visual-spec.ts screenshot per story and theme (Playwright)
```

The reasoning: a component is "done" only when its behavior is tested, its states are documented, it passes accessibility checks, and its look is pinned. Each file answers one of those questions, and the naming makes a missing one visible in the folder listing.

The stories are the source for the other two Playwright files. The story id `components-todoitem--with-delete` comes from `title: 'Components/TodoItem'` and the export name `WithDelete`. If you add a story, you add a line to the a11y and visual specs.

### ui-web Does Not Know Redux

`ui-web` has no dependency on Redux or on `core`'s store. A component receives data and callbacks through props:

```tsx
export const WithDelete: Story = {
  args: {
    onDelete: (): void => {
      /* noop */
    },
    todo: { completed: false, description: '...', id: '5', title: 'Task with a delete button' },
  },
};
```

This is what makes the five-file contract cheap. A story needs no store, no provider and no mocked API; it needs props. The same property is what would let another client reuse the components. The rule is described in [Architecture Decisions](architecture-decisions.md); here it is a practical requirement of Storybook.

### Components vs Widgets

A **component** is a single visual unit with no knowledge of the product (`button`, `modal`, `pagination`). A **widget** combines components into a piece with product meaning (`login-form`, `register-form`, `add-todo-form`), but still takes its behavior from props, for example `onSubmit`. Neither layer connects to state. That connection is done in the app, which passes selectors and dispatch callbacks down.

## Storybook as the Contract

A story is a specification of one state: `Todo`, `Done`, `LongTitle`, `WithDelete`. Together the stories of a component list everything it is supposed to do. The tests described in the next sections run against exactly these stories, so a state without a story is a state without any visual or accessibility protection.

Storybook is configured in `packages/ui-web/.storybook/`:

- `main.ts` registers the addons: `@storybook/addon-docs` (autodocs from `tags: ['autodocs']`), `@storybook/addon-a11y`, `@storybook/addon-vitest` and `@chromatic-com/storybook`.
- `preview.ts` loads `tokens.css`, the theme decorator and a router decorator, and sets the axe rules.

Two things run on the stories inside Storybook tooling:

- **addon-a11y** runs axe on each story in the Storybook UI. `parameters.a11y.test` is `'error'`, so a violation fails instead of warning.
- **addon-vitest** turns every story into a Vitest test in a real Chromium browser. It is the `storybook` project in `packages/ui-web/vite.config.ts`, run with `npm run test:storybook`. A story that throws during render fails the test.

The `unit` project in the same config runs the `*.test.tsx` files in jsdom (`npm run test`). Two projects, two jobs: jsdom for logic, a browser for rendering.

### Why Storybook Is Not Deployed Here

A common setup deploys Storybook for every pull request so that designers can review without cloning the repository. This repository does not do that. There is no Storybook deployment: the `cd.yml` workflow ("Release Frontend") deploys the web client, and Storybook has a `build:storybook` script (`npm run storybook:build` at the root) but nothing publishes the result. This is a deliberate scope decision for the reference project, not a technical limit. Run it locally with:

```shell
npm run storybook
```

If you add deployment, the natural place is a static hosting target next to the web client bucket, with a path per pull request.

## Visual Regression

Visual tests take a screenshot of every story in both themes and compare it with a stored one. They catch what unit tests cannot: a token change that shifts a color, a padding regression, a broken dark mode.

`packages/ui-web/visual-tests/helpers.ts` opens the story iframe with the theme in the URL, waits for fonts, and calls `toHaveScreenshot`:

```ts
await page.goto(`/iframe.html?id=${id}&viewMode=story&globals=theme:${theme}`);
...
await expect(page).toHaveScreenshot(`${theme}-${name}.png`);
```

Settings are in `packages/ui-web/playwright.visual.config.ts`:

```ts
toHaveScreenshot: {
  animations: 'disabled',
  maxDiffPixelRatio: 0.01,
  threshold: 0.2,
},
```

- `maxDiffPixelRatio: 0.01`: up to 1% of pixels may differ.
- `threshold: 0.2`: how different a single pixel may be (0 to 1) before it counts as different. It absorbs anti-aliasing noise.
- `animations: 'disabled'`: no flaky frames from transitions.

Commands:

```shell
npm run test:visual           # compare with snapshots
npm run test:visual:update    # regenerate snapshots after an intended change
```

### Snapshots Are Per Platform

Font rendering differs between macOS and Linux, so a screenshot taken on one never matches the other within a 1% tolerance. The snapshot path is therefore tied to a platform:

```ts
snapshotPathTemplate: 'visual-tests/snapshots/darwin/{testFileDir}/{arg}{ext}',
```

Today only `visual-tests/snapshots/darwin/` exists in the repository, and the path is hardcoded. That means the visual tests work on a developer's Mac and would fail on a Linux CI runner. This is one of the reasons the frontend CI is currently disabled (`ci.yml` has `if: false`).

Enabling it needs two changes:

1. Replace the hardcoded `darwin` in `snapshotPathTemplate` with `{platform}`, so each OS reads its own folder.
2. Generate the Linux snapshots on Linux. `.github/workflows/update-visual-snapshots.yml` exists for this: it is a `workflow_dispatch` job that runs `npm run test:visual:update` on `ubuntu-latest` and commits `packages/ui-web/visual-tests/snapshots/linux`.

Note that the workflow already commits to the `linux` folder, while the config still writes to `darwin`. Until step 1 is done, the workflow would regenerate the macOS-named folder with Linux images. The two files must be changed together.

## Accessibility Testing

Accessibility is a baseline requirement here, not an extra. The reasoning, including the legal side, is in [Styles Management](styles-management.md#why-accessibility-is-in-the-pipeline).

The implementation is `*.a11y-spec.ts` next to each component. `packages/ui-web/a11y-tests/helpers.ts` opens a story and runs axe-core scoped to `#storybook-root`:

```ts
const WCAG_TAGS = ['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'best-practice'];

const results = await new AxeBuilder({ page }).include('#storybook-root').withTags(WCAG_TAGS).analyze();
expect(results.violations, formatViolations(results.violations)).toEqual([]);
```

This checks WCAG 2.0 and 2.1 levels A and AA plus axe best practices. A failure prints the rule, the help text and the offending HTML nodes, so the report is actionable without opening a browser.

```shell
npm run test:a11y
```

What it does not do: automated checks find roughly the mechanical half of the problems (contrast, missing labels, roles). They cannot tell whether a focus order makes sense or whether a screen reader announcement is understandable. Keyboard and screen reader checks stay manual.

Contrast is the place where tokens and accessibility meet. Both themes have to pass, which is why a new color token must be checked in light and dark. The a11y spec currently runs on the default (light) theme; the visual specs cover both.

## Designer Workflow

The intended flow:

1. A designer or developer edits a token JSON file.
2. `npm run design-token:build` regenerates the outputs.
3. A pull request shows the JSON change and the CSS diff.
4. The reviewer opens Storybook, switches the theme in the toolbar and looks at the affected components.
5. Visual tests fail where the look changed; the author reviews the diffs and updates the snapshots.
6. After merge, both clients get the new values.

What works today and what does not:

| Step                                        | Status                                                      |
| ------------------------------------------- | ----------------------------------------------------------- |
| Token JSON, build, shared by web and mobile | Works                                                       |
| Storybook with theme switch, locally        | Works (`npm run storybook`)                                 |
| Unit, Storybook and a11y tests              | Work locally                                                |
| Visual tests                                | Work on macOS only; Linux needs the changes described above |
| Storybook link in the pull request          | Not available: Storybook is not deployed                    |
| CI running all of the above                 | Disabled on purpose (`ci.yml` has `if: false`)              |

So a designer without a local setup cannot yet review a token change independently. A developer can, in a few commands. The pieces that remove the gap (Storybook deployment, Linux snapshots, enabled CI) are small and listed in this chapter; they were left out because this repository is a reference, not a product with a design team.
